## 〇、为什么必须有这一阶段

截至本文件生成时，系统产出过的**每一条**结论都是 `[静态分析]`——
引擎只看过代码，**从未看过板子**。

这在项目内部是完全正常的（Phase 3/4 的定位就是静态层），
但如果就此宣称"诊断正确"，就是本项目红线（AGENTS.md 4.2）明令禁止的伪造实测。
Phase 5 的唯一目的，是把"代码里查出什么"与"板子上看到什么"对上号。

**当前系统里所有 `[实测-硬件]` 标签的条目，来源只有两种**：
① 你在 UI/接口手动提交的实测值；② 本阶段你真实采集的串口抓帧。
系统本身不产生任何一条。

## 三、第二步：6 个故障案例逐一定案

### 通用操作流程（每个案例相同）

1. 用 `apps/server/samples/<文件名>.c` **整个替换**工程里的 `main.c`
   （这些文件是完整可编译的 main.c，不是片段）。
2. 编译 → 烧录 → 复位。
3. 串口助手设置 **115200 / 8 / N / 1**，打开串口，观察 10 秒。
4. 把串口窗口里看到的**原始内容**复制下来（不要手敲、不要改写）。
5. 在 UI 左栏「硬件实测记录」粘贴 → 选案例号 → 点「提交抓帧并重诊断」。
6. 记录下表所有字段。

### ⚠️ C2 的编译期陷阱（2026-10-25 已修，务必保持）

SPL 的 `stm32f10x.h` 里 `HSE_VALUE` 被 `#if !defined HSE_VALUE` 保护（默认 8MHz）。
因此 `#define HSE_VALUE` **必须写在 `#include "stm32f10x.h"` 之前**才生效。

原先样例把它写在 include 之后 —— 结果是：静态分析照样"检出"故障，
但编译出来的固件波特率完全正常，**上板根本不会有乱码现象**。
这是"静态结论与实测脱节"的典型反例，已修正并在文件头写明原因。
若你发现 C2 上板没乱码，第一件事就是检查这个顺序。

## 五、回填系统的路径

1. UI 左栏 → 「硬件实测记录」→ 粘贴抓帧 → 选案例号 → 提交抓帧并重诊断。
2. 后端自动做三件事：
   - 落库 `hardware_tests`（`evidence_tag` 只能是 `HW_TEST` / `SIM_TEST`，
     填 `STATIC` 会被接口和数据库 CHECK 双重拒绝）；
   - 调用 `parse_serial_capture` 判定 EMPTY / GARBLED / NORMAL（**不改写原文**）；
   - 重跑诊断，把现象与各案例预期做比对，比对结论一律标 `[推断]`。
3. 中栏出现「串口实测现象」卡；报告新增「六、硬件实测记录」章（含原文与比对表）。

**标签纪律（系统强制，不是提示）**：
- 抓帧判读 → `[实测-硬件]`（数据是你采的）
- "乱码意味着波特率不符" → `[推断]`
- "实测现象与某案例预期一致" → `[推断]`，**一致只表示未被证伪，不等于证实**

## 八、无法复现时怎么办（先约定，避免临场改口径）

1. **如实记录**：在本文件该案例记录表勾「未复现」并写原因。
2. **修预期表**：若判断是预期写错 → 改 `docs/corpus/phenomena_map.json` 对应项，
   并在改动处注明"Phase 5 实测修订"。
3. **修样例**：若判断是样例注入手法无效 → 改 `samples/*.c`，重跑 `samples_test.py`。
4. **剔除**：若该故障在本板卡上根本无法复现 → 从正式实测集剔除，
   在 Phase 6 评测中**不计入分母**，并在答辩材料中写明。
5. **绝不**：不修改实测值去迁就预期，不删掉失败记录，不把"应该会这样"写成实测。

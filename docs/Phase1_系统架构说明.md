# Phase 1 交付物 ③ 系统架构说明

> 证据标签：架构决策为 `[推断]`（工程判断）；本机环境相关结论为 `[静态分析]`（2026-10-25 环境核查）。
> 本文不含性能基准数字。
> 生成时间：2026-10-25。所属阶段：Phase 1。

## 一、架构总览

```
┌───────────────────────────────────────────────────────────────┐
│ 前端  React 18 + TypeScript + Vite + Tailwind                 │
│  P1 列表 / P2 提交 / P3 工作台 / P4 验证 / P5 报告 / P6 知识库 │
│  状态：Zustand  流式：EventSource(SSE)                         │
└───────────────────────┬───────────────────────────────────────┘
                        │ REST + SSE  (http://localhost:8000)
┌───────────────────────▼───────────────────────────────────────┐
│ 后端  Python + FastAPI                                        │
│                                                               │
│  ┌─ API 层 ─────────────────────────────────────────────┐    │
│  │  /api/tasks  /api/artifacts  /api/diagnose  /api/... │    │
│  └───────────────────────┬──────────────────────────────┘    │
│  ┌─ 编排层 Orchestrator ─▼──────────────────────────────┐    │
│  │  诊断状态机 + 步骤规划 + Trace 记录（自研，非框架）   │    │
│  └───┬──────────────┬──────────────┬────────────────────┘    │
│      │              │              │                          │
│  ┌───▼────┐   ┌─────▼──────┐  ┌────▼──────────────────┐      │
│  │ 工具层 │   │  RAG 层     │  │  模型层 ModelRouter   │      │
│  │ 6 工具 │   │ 规则库+卡片 │  │  云端 / 本地 / 规则兜底│      │
│  └───┬────┘   └─────┬──────┘  └────┬──────────────────┘      │
│      │              │              │                          │
│  ┌───▼──────────────▼──────────────▼────────────────────┐    │
│  │ 存储层  SQLite（任务/证据/trace）+ 本地文件（材料）   │    │
│  └──────────────────────────────────────────────────────┘    │
└───────────────────────────────────────────────────────────────┘
```

**分层职责一句话**：
- **前端**负责呈现与交互，不做任何诊断判断。
- **API 层**负责校验与序列化，不含业务逻辑。
- **编排层**负责"下一步做什么"，是全系统唯一的流程控制点。
- **工具层**产出**确定性事实**。
- **RAG 层**产出**可追溯的知识**。
- **模型层**负责**推理与表达**，其输出永远带 `[推断]` 标签，永不直接等同于结论。
- **存储层**负责全链路留痕。

## 二、前端架构

| 模块 | 职责 | 技术 |
|---|---|---|
| `pages/` | 6 个页面容器 | React Router |
| `components/task/` | 任务卡片、状态徽章、材料树 | Tailwind |
| `components/timeline/` | 诊断时间线、工具调用展开卡 | Tailwind |
| `components/hypothesis/` | 候选根因卡、证据列表、证据标签徽章 | Tailwind |
| `components/verification/` | 验证步骤清单、实测回填表单 | React Hook Form |
| `store/` | 任务状态、流式事件累积、UI 状态 | Zustand |
| `api/` | REST 客户端 + SSE 订阅封装 | fetch / EventSource |
| `types/` | 与后端 Pydantic 模型对齐的 TS 类型 | TypeScript |

**流式策略**：诊断过程用 SSE 推送结构化事件（不是裸文本流），前端按事件类型增量渲染时间线。这样做的好处是——**过程可视化直接来自真实事件，而非前端伪造的动画**（对应创新方向 B 与验收「UI 展示与实际后台能力一致」）。

## 四、模型层（ModelRouter）

### 4.1 三级降级链

| 级别 | 提供方 | 触发条件 | 输出标签 |
|---|---|---|---|
| L1 | 云端模型（可配置：DeepSeek / 通义 / 智谱 / OpenAI 兼容） | 有 API Key 且网络可用 | `[推断]` |
| L2 | 本地 Ollama（`qwen2.5:7b` 通用 / `qwen2.5-coder:7b` 代码推理；**本机已拉取，无需下载**） | L1 失败 / 未配置 / 用户选择离线 | `[推断]` |
| L3 | 规则层兜底（纯确定性工具 + 规则库） | L1、L2 均不可用 | 仅 `[静态分析]`，UI 显式提示降级 |

**本机模型实测支撑**（`[静态分析]` 2026-10-25）：Ollama 客户端 0.32.0 已装，已拉取 `qwen2.5:7b`、`qwen2.5:3b`、`qwen2.5-coder:7b`、`bge-m3`、`nomic-embed-text`（合计约 12 GB）。
→ L2 降级链**真实可行且无需新增下载**，符合「未经批准不得下载模型」的禁令。
⚠️ 探测时 Ollama **服务未运行**，运行时需先启动；此项列为 Phase 3 环境检查项。

**关键约束**：
- 模型 provider **必须可配置**（`PROJECT_PLAN.md` 第六节要求），通过环境变量选择。
- 记录模型名称、关键参数（temperature、max_tokens）、调用耗时、错误类型（**不记录密钥**）。
- 模型输出**必须**经结构化校验；解析失败重试，达到上限后转 L3，绝不把非法输出当结论。
- **不得把模型切换能力当作产品创新**（`PROJECT_PLAN.md` 明确禁止）——文档与答辩中不将其列为核心创新点。

### 4.2 云端调用的内容边界

- 发送前对材料做裁剪：仅发送与诊断相关的代码片段、日志片段、现象描述。
- UI 明示「本次诊断将向云端模型发送约 N 字符」。
- 用户可选择「仅本地模式」，此时强制 L2/L3。

## 五、RAG 层（承接 D1 决策：语料必须自建）

### 5.1 三层知识结构

| 层 | 内容 | 是否入库 | 说明 |
|---|---|---|---|
| **L1 结构化规则库** | 症状 → 候选根因 → 证据检查项 → 引用章节 → 验证步骤 | ✅ 自建 | 自撰，JSON 结构，按「外设 + 症状 + 芯片」索引 |
| **L2 知识卡片** | 40 条自撰知识卡片 | ✅ 自建 | 每条含：标题、正文（自撰）、`source_ref`（章节级引用）、适用芯片、不适用警告 |
| **L3 官方手册 + 本地知识库** | RM0008、F103 数据手册、本地 350+ 条目知识库 | ❌ **不入库** | 仅开发期参考，用于事实核对 |

**合规红线（D1 后果）**：
- ✅ 允许：寄存器名、位定义、配置流程等**公有技术事实**（自撰表述）
- ✅ 允许：章节级引用，如「依据 RM0008 第 19 章 USART」
- ❌ 禁止：手册原文段落
- ❌ 禁止：本地知识库原文（即便原文标注「已审」）
- ❌ 禁止：手册章节截图

### 5.2 检索策略

| 检索路径 | 方法 | 产出 |
|---|---|---|
| 主路径 | **结构化规则匹配**（按外设/症状/芯片确定命中） | 候选根因集合 + 应执行的检查项 |
| 辅路径 A | **BM25 关键词检索**（知识卡片，纯本地） | 精确词命中 + 可解释排序依据 |
| 辅路径 B | **bge-m3 向量检索**（Ollama 本地嵌入，**本机已拉取**） | 语义/同义表述召回 |
| 融合 | 规则命中优先 → BM25 与向量各取 Top-K → 加权合并 | 最终结果 + 来源引用 |

**为什么用混合检索而不是纯 BM25**（`[推断]`，依据 2026-10-25 本机实测）：
Phase 1 环境核查发现本机 Ollama **已拉取 `bge-m3` 中文嵌入模型**（约 12GB 模型库中含此模型），向量检索**无需任何新增下载**，原「为避免下载嵌入模型而放弃向量」的理由不再成立。语料规模虽小（40 条），但用户故障描述的表述差异较大（如"串口没反应" vs "无输出"），语义召回能明显提升命中率；BM25 保留则可解释性强、精确词命中准。两者互补且均为本地资源。

**降级路径**：若向量检索实现耗时超预期，退化为纯 BM25 仍可工作——符合 Phase 0 削减原则，不影响核心闭环。

### 5.3 可追溯性强制

每条检索结果必须携带：
- `source_ref`（章节级引用，如 `RM0008 Ch.19 USART`）
- `applicable_chip`（适用芯片）
- `confidence_note`（适用条件与不适用警告）
- 缺失 `source_ref` 的条目 → UI 标注 `[来源未确认]`，**不得**当作权威依据

## 六、Agent 与工具层

### 6.1 编排器设计（自研轻量状态机）

**为什么不直接用 LangChain / LangGraph**（`[推断]`）：

| 维度 | 自研轻量编排器 | 通用 Agent 框架 |
|---|---|---|
| 可解释性 | 步骤由规则驱动，流程确定 | 框架内部逻辑复杂，答辩难以讲清 |
| 赛事合规（须能解释全部代码） | ✅ 代码量小、逻辑自明 | ⚠️ 需额外解释框架行为 |
| 可复现 | 同输入 → 同步骤序列 | 受框架版本与随机性影响 |
| 开发成本 | 中（需自己写 trace） | 低（开箱即用） |
| 风险 | 需自行处理工具调用解析 | 抽象泄漏时调试困难 |

**结论**：选自研。核心理由是赛事要求「须能解释全部代码逻辑」+ 创新方向 B 要求「执行过程可追踪、可复现、可评测」。

**编排器三要素**：
1. **状态机**：任务状态（PRD 第四节）驱动，非法迁移直接拒绝。
2. **规划器（planner）**：规则驱动的步骤规划——根据「已有材料类型 + 症状分类」决定下一步调用哪个工具。不是让模型自由发挥。
3. **Trace 记录器**：每一步、每次工具调用、每次模型调用全部落库，前端时间线直接读 trace。

**工具调用控制**：
- 模型只能从**白名单**中选择工具，参数经 Pydantic 校验。
- 服务端强制限制单任务工具调用次数上限，防死循环。
- 工具失败如实记录，不允许模型把失败包装成成功。

### 6.2 六个诊断工具

| 工具 | 输入 | 输出 | 产出标签 | 设计必要性 |
|---|---|---|---|---|
| `parse_build_log` | 编译/链接日志文本 | 错误与警告结构化列表（文件、行号、类型、原文片段） | `[静态分析]` | 编译错误常被误认为硬件问题；必查 |
| `analyze_c_code` | C 源码 + 文件路径 | 初始化调用链、USART/GPIO/RCC/NVIC 配置提取、可疑点 | `[静态分析]` | 核心：把"用户代码"变成可检查的结构化事实 |
| `check_uart_config` | `analyze_c_code` 输出 + 芯片型号 | 配置项一致性检查：引脚复用、TX/RX 模式、时钟使能、NVIC、重映射 | `[静态分析]` | UART 故障高频根因集中在此 |
| `calc_baud_error` | 时钟配置 + 目标波特率 | 实际波特率、误差百分比、是否在容差内 | `[静态分析]`（确定性计算） | 乱码问题的决定性判据；交给模型算会出错 |
| `search_reference` | 查询串 + 外设/芯片上下文 | 命中规则与知识卡片 + `source_ref` | `[静态分析]` | RAG 入口，可追溯性载体 |
| `record_test_result` | 验证步骤 ID + 用户实测数据 | 假设更新（置信度变化 + 理由）、任务状态迁移 | `[实测-硬件]`（用户填） | 闭环关键；Agent 不得代填 |

**关于"不要为展示能力而调工具"**：planner 为每个工具定义了**明确的触发条件**（如：仅在提交材料含编译日志时才调用 `parse_build_log`），不满足条件则跳过并记录跳过原因。

**工具输出必须区分**：确定性检查结果 vs 模型推断。工具只产出前者；后者由模型层产出且带 `[推断]` 标签。

## 七、存储层

| 对象 | 存储方式 | 理由 |
|---|---|---|
| 任务、假设、证据、trace、报告 | **SQLite**（单文件） | 零部署，评审 `git clone` 后无需装数据库即可运行 |
| 上传材料原文 | 本地文件系统（`data/tasks/{task_id}/`） | 大文本不入表；路径校验防穿越 |
| 知识语料 | 仓库内 JSON/Markdown 文件 | 版本可控，评审可见 |
| 检索索引 | 启动时内存构建（40 条，无需持久化索引） | 规模极小，避免索引文件同步问题 |

**为何不用 PostgreSQL + pgvector**（承接 Phase 0 决策）：项目为单用户本地工具，引入数据库服务会显著增加评审复现成本，收益不匹配。已砍。

## 八、端到端关键数据流

```
用户提交材料
   ↓ API: POST /tasks/{id}/artifacts
存储材料 → 任务状态 draft → analyzing
   ↓ API: GET /tasks/{id}/diagnose (SSE)
编排器 planner 规划步骤 ──► SSE: step_start
   ① parse_build_log      ──► SSE: tool_call → tool_result → evidence_added
   ② analyze_c_code       ──► SSE: tool_call → tool_result
   ③ check_uart_config    ──► SSE: tool_call → tool_result → evidence_added
   ④ calc_baud_error      ──► SSE: tool_call → tool_result → evidence_added
   ⑤ search_reference     ──► SSE: tool_call → tool_result → evidence_added
   ⑥ 模型层综合推理        ──► SSE: hypothesis_update（含 [推断] 标签 + 置信度）
   ↓
任务 → awaiting_verification ──► SSE: done
用户执行验证 → POST /verifications/{step}/result（record_test_result）
   ↓
假设更新 → hypothesis_update（置信度变化 + 理由）
   ↓ 循环或收敛
GET /reports/{id} → 诊断报告
```

**每一次 SSE 事件同时写入 trace 表**，断线重连时按 `last_event_id` 增量补发。

## 九、架构与评分项的对应

| 评分项 | 架构承载 |
|---|---|
| 大模型集成质量 8% | ModelRouter 三级降级 + 结构化输出校验 + 元数据记录 |
| Agent/工作流 8% | 自研编排器 + 6 工具 + 全量 trace + 规则驱动 planner |
| RAG 6% | 自建双层语料 + 章节级引用 + BM25 可解释检索 |
| 多模态 5% | Phase 7 最小实现：波形图上传 + 人工标注（**非自动识别**） |
| AI 安全与可控 4% | 不执行用户代码 + 工具白名单 + 提示词注入隔离 + 密钥环境变量 + 脱敏 |
| MCP/工具集成 4% | Function Calling + 工具注册表（**MCP 已砍**） |
| 创新性 25% | 证据驱动诊断（A）+ 可验证工作流（B）+ 真实硬件闭环（C） |

## 十、架构决策记录（ADR 摘要）

| 编号 | 决策 | 备选 | 理由 |
|---|---|---|---|
| ADR-01 | 前端 React+TS+Vite | Vue3 / Next.js | 赛事重点考察前端；Vite 启动快；无需 SSR |
| ADR-02 | 后端 Python+FastAPI | Node/Express | Python 生态适合文本解析与模型 SDK；FastAPI 自带 OpenAPI |
| ADR-03 | SQLite 单文件 | PostgreSQL+pgvector | 零部署，评审可复现；项目规模不匹配重型 DB |
| ADR-04 | 自研编排器 | LangChain / LangGraph | 可解释、可复现、能讲清全部逻辑（赛事合规要求） |
| ADR-05 | BM25 + bge-m3 混合检索 | 纯 BM25 / 纯向量 | 嵌入模型已本地可用（零下载）；语义召回与可解释性兼得 |
| ADR-06 | 语料全自建 | 用本地知识库 350+ 条 | **D1 决策：不得入库** |
| ADR-07 | 不自动编译用户工程 | 调用 Keil 编译 | 安全（不执行用户代码）+ 评审可复现 |
| ADR-08 | 波形图为人工标注 | 自动波形识别 | 时间预算不足；诚实标注优于虚假智能 |
| ADR-09 | SSE 结构化事件 | WebSocket / 裸文本流 | 单向推送足够；结构化事件直接驱动时间线 UI |

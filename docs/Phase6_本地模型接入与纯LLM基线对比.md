## 二、模型能做什么、不能做什么

这是本次接入**最核心的设计**，也是答辩时最该讲清楚的一点。

**能做（两件事）**
1. 把工具**已经查出**的结论用工程师的话解释清楚。
2. 补充"用户下一步可以在板子上做的检查动作"。

**不能做（强制，代码层保证）**
- ❌ 不参与候选根因判定与评分。`llm_assist` 在排序**之后**执行，
  模型拿到的只是已确定的候选，返回的东西不写回候选列表。
- ❌ 不标注证据等级。输出恒为 `[推断]`，标签由系统统一加。
- ❌ 不得声称实测。守卫会拦"已实测 / 已验证 / 已确认 / 经实测"等表述。
- ❌ 不得新增字段。JSON 只允许 `summary / extra_steps / cautions` 三个键。

实测证据：`llm_smoke.py` 断言"开启模型后候选与评分不变"——
规则层基线 `{R-S1-01: 1.5}`，开启模型后**完全一致**。

## 三、输出守卫（四道闸）

模型输出在离开 `app/llm/guard.py` 之前**不算证据**：

| 闸 | 规则 | 不通过时 |
|---|---|---|
| ① 结构化 | 必须是 JSON，字段在白名单内 | 整段作废 |
| ② 证据越权 | 出现证据标签或"已实测/已验证"类表述 | 整段作废 |
| ③ 事实锚定 | 解释必须落到本次真实查出的检查项 | 由提示词约束 |
| ④ 长度 | summary ≤ 400 字、步骤 ≤ 4 条 | 截断 |

**守卫自己也出过 bug，已修（值得记一笔）**：
- 初版给"已验证"加了后缀白名单（通过/成功/正确），
  「已验证该引脚配置无误」能绕过 → 改为不限后缀。
- 初版对步骤列表里的越权内容是**静默丢弃**，没上报 →
  静默降级本身就违反项目纪律，改为整段作废并写明原因。

## 四、降级链（模型挂了不影响诊断）

```
① 云端 provider（配置不全即跳过，绝不"半配置"运行）
② 本地 Ollama（默认）
③ 规则层兜底 —— 系统行为与接入前完全一致
```

`narrate()` **永不抛异常**：不可用 / 超时 / 输出非法 / 被守卫拒绝，
一律返回 `degraded=True` 并写明原因，诊断照常完成。
离线时原因会写进 `limitations`，并出现在报告第七章。

覆盖场景（`llm_test.py` 离线替身，27/27）：正常输出、越权、非 JSON、
调用异常、服务不可达、未启用、空解释、云端未配置。

## 五、纯 LLM 基线对比（R28 已解除）

### 5.1 公平性处理

| 项 | 做法 |
|---|---|
| 同一批材料 | 源码 + 现象 + **编译日志**（初版漏传日志，已修——否则 N-02 对模型不公平） |
| 同一候选空间 | 模型只能从同一份 23 条规则目录里选编号，或输出 INSUFFICIENT |
| 同一判定口径 | 正例看 Top-1 是否落入期望规则集；负例看是否命中禁用规则 |
| 不修饰失败 | 输出非法 JSON、编造编号，一律记失败 |
| 重复采样 | 每例 **3 次**（7B 有输出抖动，单次结果不可信） |

### 5.2 结果（`eval/results/llm_baseline_20261025_180806.json`）

| | 规则层 + 工具 | 纯 LLM（qwen2.5:7b ×3） |
|---|---|---|
| 正例 Top-1 命中 | **6/6** | **6/6**（三次全中） |
| 负例误报 | **0** | **1**（N-01 空材料硬给 R-X-01） |
| 输出稳定（三次一致） | 确定性 | 9/9 |
| 无效输出 | 0 | 0 |
| 平均单次耗时 | <10 ms | 2301 ms |

**逐例**

| 用例 | 规则层 | 纯 LLM ×3 | 说明 |
|---|---|---|---|
| P-01 ~ P-06 | 全部命中 | 全部命中且三次一致 | **打平** |
| N-01 材料严重不足 | 不给根因（insufficient） | R-X-01 ×3 | LLM 硬猜 |
| N-02 真实问题是链接错误 | R-X-01 | R-S1-01 ×3 | LLM 忽略了编译日志 |
| N-03 提交的是 I2C 代码 | 不给 UART 结论 | R-S1-05 ×3 | 见下方口径说明 |

### 5.3 必须如实说的三点

1. **正例打平，没有"我们更准"这回事。** 在 6 个注入型故障上，
   直接把源码丢给 7B 模型和我们跑规则层，命中率一样。
   谁要是拿"我们的系统比大模型准"去答辩，是站不住的。
2. **N-03 存在口径盲区。** 模型给的是 `R-S1-05`，不在 Phase 2 预设的禁用清单内，
   按脚本口径不算误报；但按"提交 I2C 却给 UART 结论"的实质判定，它就是误报。
   **若按实质口径，LLM 负例误报应为 2，规则层仍为 0。**
3. **样本只有 9 例、单次 3 采样，不足以支撑任何准确率结论**，只能说明趋势。

### 5.4 那我们的价值在哪

基线对比逼出来的答案，比"我们更准"更有说服力：

- **可追溯**：每条结论能指到规则号 + 工具调用 + 耗时 + 入参出参（`/tool-runs`）。
- **不硬猜**：材料不足时说"不确定"，而不是给一个看着像根因的答案（N-01 的差异）。
- **守边界**：提交 I2C 代码不会被套上 UART 结论（N-03 的差异）。
- **能接实测**：用户回填的抓帧/波特率是真正的 `[实测-硬件]`，
  模型再聪明也产不出这个——它只能产出 `[推断]`。
- **确定性 + 快**：规则层 <10ms 且结果稳定，模型 2.3s 且有抖动。

**一句话**：模型的强项是"猜得准"，我们的强项是"说得清、验得过、不瞎编"。

## 六、接入前后对比（默认行为不变）

| 场景 | 行为 |
|---|---|
| 默认（API 不传 `use_llm`） | 纯规则层，`llm_assist` **不注册**，工具清单仍是 8 个 |
| `use_llm=1` | 注册并调用 T-08，trace 里可见，失败只记 error |
| 模型离线 | 降级，诊断照常完成，原因写进 limitations 与报告第七章 |
| 评测 / 冒烟 / 消融 | 全部走默认路径，**不受模型可用性与耗时影响** |

另修一个真问题：SSE 单步等待原为 60s，模型冷启动（4.7GB 载入显存）
可达数十秒，会被误报成"诊断超时"→ 改为 `max(60, LLM_TIMEOUT_S + 60)`。

## 一、变更摘要

### 1. 新增工具注册表 `app/engine/registry.py`

Phase 3 里编排层裸调工具函数，导致「调用不可留痕 / 失败掀翻整轮 / 工具无法单测」。本批把调用收敛为一个入口：

| 能力 | 实现 |
|---|---|
| 统一留痕 | `ToolRun` 记录 seq / status / reason / input_sum / output_sum / duration_ms / error |
| 失败隔离 | 工具抛异常只记 `status="error"` 并返回 `None`，**不向上抛** |
| 跳过可追溯 | `skip()` 必须写明原因，「没做」与「做了没问题」绝不混为一谈 |
| 可单测 | 工具脱离编排层可独立调用与断言 |

### 2. 新增两个工具（T-04r / T-06）

| 工具 | 解决什么 | 对应规则 |
|---|---|---|
| `analyze_isr_body`（T-06） | Phase 3 对中断类规则只能看到「有没有写 ISR、名字对不对」，R-S6-03 / R-S6-04 恒为 unknown，C5/C6 无法量化 | R-S6-03（是否读 DR 清 RXNE）、R-S6-04（是否处理 ORE） |
| `infer_actual_fck`（T-04r） | 「波特率所依据时钟与实际不符」此前无法判定：静态看不出实际时钟。用户给出**实测波特率**后，按 `fCK = baud × 16 × DIV` 纯算术反推真实总线时钟 | R-S2-01 |

配套改动：`cparse.py` 增加 ISR 函数体提取（花括号配对）；`uart_check.py` **删除**原先硬编码的 R-S6-03/04 `unknown`——恒返回 unknown 会让用户误以为「检查过但判不了」，实际是没检查，属误导。

### 3. 证据纪律的细化（重要）

反向比对场景同时存在两类证据，本批强制分开标注：

- 用户提交的**实测观测值** → `[实测-硬件]`（来源：用户，非系统生成）
- 由观测值**推导出的**总线时钟结论 → `[推断]`

绝不把推断结果标成实测。端到端测试断言了这两个标签必须同时出现且各归其位。

### 4. 多步诊断入口

- 引擎新增 `followups`：证据不足时明确列出「要继续诊断需要补充什么」，例如乱码场景会要求提供实测波特率与实际总线时钟。
- 新增 `POST /api/tasks/{tid}/reassess`：用户补齐信息后重新诊断，走**与 SSE 完全相同的引擎路径**（不存在两套诊断逻辑）。
- 新增 `GET /api/tools`、`GET /api/tasks/{tid}/tool-runs`（含耗时/入参/失败原因）、`GET /api/tasks/{tid}/followups`。
- 报告新增「下一步需要补充的信息」章节。

`apps/server/samples/`：C1–C6 各一对（故障版 + 对照版）。

| 案例 | 注入点 | 预期规则 | 备注 |

证据等级说明：以上测试全部属于 `[静态分析]` 层级的验证。它们证明的是「引擎能按规则检出注入的配置缺陷」，**不证明**这些缺陷在真实板卡上会产生预期现象——现象层面验证属 Phase 5，须由用户上板实测后回填。

### 测试暴露的两个真实缺陷（已修）

1. **`ToolSpec` 字段顺序错位**：`register()` 传参顺序与 dataclass 定义不一致，导致 `fn` 被赋成字符串，调用时报 `TypeError: 'str' object is not callable`。由于注册表捕获异常，这个 bug 被"静默"成 error 状态——正是测试里断言「异常原因应含 RuntimeError」才发现。
2. **`HSE_VALUE` 解析把 `uint32_t` 的 "32" 当成晶振频率**：`#define HSE_VALUE ((uint32_t)8000000)` 提取出 32。**这个 bug 让 C2 故障版"假通过"**（32 ≠ 8000000 恰好判成 violated），是对照版测试不误报失败才暴露出来。已改为先剥离类型转换再取数字。

方法论收获：故障版单独测试会产生假阳性，**必须成对测试**（故障版命中 + 对照版不误报）才算数。

## 四、未解决问题

1. **波特率容差 2% 仍标 `[待验证]`**，需 Phase 5 实测校准。
2. **ISR 体分析只覆盖函数体内直接调用**，跨函数封装（如 `Uart1_RxHandler()` 内部再读 DR）会漏判，已作为 limitation 写进工具输出。
3. **C4 / C6 案例仍是 `[待验证]`**（Phase 2 即如此标注），本批只做了静态层面的样例设计，未上板。
4. **反向推断依赖用户提供的实测波特率精度**；若串口助手自动识别错误，推断随之错误——已写入 `limitations` 并在 UI 上提示。
5. **`analyze_c_code` 仍不覆盖**：宏封装调用、跨文件初始化、条件编译分支（已如实声明 limitation）。

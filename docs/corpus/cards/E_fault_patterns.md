## card-29 · 完全无输出（S1）的排查主线

**标签**：`symptom` `s1` `no-output` `排查`

**正文**：「TX 上完全没有数据」的排查应按由外到内的顺序收敛：① 先确认程序在运行（如同一端口的 LED 是否闪烁）；② 确认 USART 与 GPIO 端口时钟均已使能；③ 确认 TX 引脚模式为复用推挽；④ 确认所用引脚与 USART 实例匹配（含重映射与 AFIO 时钟）；⑤ 确认 USART 已使能且发送函数被调用到；⑥ 最后才考虑物理层（接线交叉、共地、电平匹配）。判别要点：若直接测量 TX 引脚有波形而 PC 端收不到，问题在链路而非 MCU 配置；若 TX 引脚连空闲高电平都没有，问题在 MCU 侧配置或程序未运行。

**source_ref**：本条目自撰归纳（排查流程）

**applicable_chip**：STM32F103C8T6

**不适用警告**：排查顺序是启发式，不是判定规则；多因并发时需逐项排除，不可因发现一个问题就停止排查。

## card-30 · 乱码（S2）的排查主线

**标签**：`symptom` `s2` `garbage` `baudrate` `排查`

**正文**：「有输出但内容错乱」说明发送链路基本通畅，问题集中在**时序与格式**：① 双方波特率是否一致，且 MCU 侧实际波特率是否由真实 PCLK 换算（查时钟源、PLL、分频）；② 数据位/校验位/停止位是否一致；③ 是否误启用了硬件流控而未接线；④ 电平是否匹配（TTL 与 RS232）；⑤ 波特率取整误差是否在可接受范围。判别要点：低波特率正常而高波特率乱码，指向时钟精度或分频误差；所有波特率都乱码但规律性错乱（如固定字符映射错误），更可能是帧格式或电平问题；收到 0x00 或 0xFF 序列，常见于波特率严重偏差或开漏无上拉。

**source_ref**：本条目自撰归纳（排查流程）

**applicable_chip**：STM32F103C8T6

**不适用警告**：上述现象对应关系为经验性归纳 `[推断]`，本项目未经系统实测验证，不得作为确定结论使用。

## card-31 · 单向通（S4）的判别价值

**标签**：`symptom` `s4` `one-way` `判别`

**正文**：「能发不能收」或「能收不能发」是最有价值的诊断线索之一，因为它能直接排除一大类根因：波特率错误通常同时影响两个方向，引脚模式错误（TX 配成输入）通常只影响发送，而未使能接收（`USART_Mode_Rx` 缺失或 RXNE 未开）只影响接收。因此确认单向通之后，排查范围应收缩到**方向相关**的配置项：RX 引脚模式、接收使能、RXNE 中断使能与 NVIC 挂接、以及接收端的软件处理（是否读取、是否清标志）。同时也要注意反向验证：所谓「能发」是否真的是 MCU 发出的，还是 PC 端自发自收的错觉。

**source_ref**：本条目自撰归纳（判别思路）

**applicable_chip**：STM32F103C8T6

**不适用警告**：单向通也可能由物理层造成（如 RX 线断线、TX/RX 未交叉），静态分析无法判定，需用户实测确认。

## card-32 · printf 无输出与直接发送正常（S5）

**标签**：`symptom` `s5` `printf` `retarget` `高频故障`

**正文**：`printf` 是 C 库函数，它本身并不知道数据要发往哪里，需要通过重定向下层输出函数把它接到 USART 上（在 ARMCC/Keil 工具链下通常是实现 `fputc`，GCC 常用 `_write`/`__io_putchar`）。因此「直接调用 `USART_SendData` 能收到字节，但 `printf` 完全没有输出」是一个非常有判别力的现象：它证明 USART 外设、引脚、波特率、接线全部正常，问题被锁定在**软件层的重定向**上。排查方向依次为：是否实现了重定向函数、函数内是否正确等待并发送、该函数所在文件是否参与了编译链接、以及是否启用了 MicroLIB（未启用时半主机调用可能导致程序在调用 `printf` 处停滞）。

**source_ref**：工具链运行时库重定向机制，非 MCU 手册内容

**applicable_chip**：STM32F103C8T6

**不适用警告**：重定向入口函数随工具链不同而不同（Keil/ARMCC 与 GCC 不同），需按实际编译器选择实现方式。

## card-33 · 半主机（semihosting）导致程序停滞

**标签**：`semihosting` `microlib` `keil` `printf` `陷阱`

**正文**：在不启用 MicroLIB、又未做半主机禁用处理的 Keil 工程中调用 `printf` 等标准 IO 函数，程序可能触发半主机机制——它试图把 IO 请求交给调试主机处理，而在没有调试器支撑的运行环境下，常见结果是程序在该调用处停滞或行为异常。典型现象是「程序在 `printf` 之前的部分正常执行，之后的代码（如 LED 翻转、后续发送）完全不动」。处理方式有两种：在 Keil 工程 Target 选项中勾选 Use MicroLIB，或在代码中做禁用半主机的处理。此项属于工具链工程配置范畴，仅凭 C 源码无法判定，需结合工程配置或实测现象判断。

**source_ref**：工具链（Keil MDK）工程配置相关，非 MCU 手册内容

**applicable_chip**：STM32F103C8T6

**不适用警告**：本条针对 Keil/ARMCC；GCC/Makefile 工程需另行实现系统调用桩函数，机制不同。

## card-34 · 接线：交叉、共地与自发自收验证

**标签**：`hardware` `wiring` `gnd` `验证`

**正文**：两个串口设备相连时，发送端要接对方的接收端，即 USB-TTL 的 RXD 接目标板 TX、TXD 接目标板 RX；同时两侧必须**共地**，否则没有共同的电平参考，信号无法被正确判决。排查硬件链路最有效的第一步是**自发自收**：把 USB-TTL 的 TXD 与 RXD 短接，用串口助手发送并接收，若数据能原样回来，说明转换器与 PC 侧工具正常，问题在目标板或接线；若自发自收都不通，问题在转换器、驱动或串口助手设置，与 MCU 代码无关。这一步能把问题域一分为二，避免在 MCU 侧做无谓排查。

**source_ref**：本项目归纳（硬件连接通用实践），非手册内容

**applicable_chip**：不限

**不适用警告**：本条属硬件层，静态分析无法判定，必须由用户实测确认；未共地时测量结果无意义。

## card-35 · 电平匹配：TTL 与 RS232

**标签**：`hardware` `level` `ttl` `rs232` `安全`

**正文**：STM32 的 IO 为 TTL 电平（3.3V 体系，高电平约 3.3V、低电平 0V），而传统 RS232 使用正负电压（通常 ±3V 至 ±15V，且逻辑极性相反）。把 MCU 引脚直接接到 DB9 的 RS232 接口上，不仅通信必然失败，还**可能损坏 MCU 引脚**；两者之间需要 MAX232 之类的电平转换芯片。日常调试推荐使用 USB-TTL 转换器（CH340、CP2102、FT232 等），并确认其 IO 电平为 3.3V 或标注为 5V 容忍；5V 电平直接接到非 5V 容忍的 F1 引脚上同样存在风险。

**source_ref**：接口电平通用工程实践，非 MCU 手册内容

**applicable_chip**：STM32F103C8T6

**不适用警告**：是否 5V 容忍需查芯片数据手册的引脚定义表（`FT` 标记），不同引脚容忍能力不同，不得一概而论。

## card-36 · 丢字节与接收缓冲区设计

**标签**：`usart` `buffer` `loss` `接收` `isr`

**正文**：USART 接收是单字节缓冲（无 FIFO），新字节到来前旧字节必须被取走，否则触发溢出。因此接收侧的设计原则是**中断里只做最少的动作**：读取字节、写入缓冲区、清标志，然后立即退出；数据的解析与处理放到主循环中进行。若在主循环里做长延时（数百毫秒级）又采用轮询接收，字节间隔内无法及时读取必然丢数据；若在中断里做耗时操作（如耗时的字符串处理、调用发送函数忙等），同样会阻塞后续接收。表现为「单次发送正常、连续发送丢字节」时，应优先检查这两类设计问题，而不是怀疑波特率。

**source_ref**：RM0008 Ch.19 USART（接收缓冲）；设计原则为本条目自撰

**applicable_chip**：STM32F103C8T6

**不适用警告**：DMA 接收可显著降低 CPU 负担，但属于本项目 MVP 之外的范围，当前不支持相关诊断。

## card-23 · 外设中断与 NVIC 是两级开关

**标签**：`nvic` `interrupt` `两级使能` `高频故障`

**正文**：要让 USART 接收中断真正触发，需要**两级使能**：第一级是 USART 外设内部的中断允许（如 `USART_ITConfig(USART1, USART_IT_RXNE, ENABLE)`），决定外设是否产生中断请求信号；第二级是 NVIC（内核的中断控制器）中对应 IRQ 通道的使能（通过 `NVIC_Init` 设置 `NVIC_IRQChannel` 与 `NVIC_IRQChannelCmd = ENABLE`），决定该请求能否送达 CPU。两者缺一不可——只开第一级，外设标志会产生但 CPU 不会进入中断；只开第二级，没有中断源也不会触发。这是「中断进不去」类问题的首要检查项。

**source_ref**：RM0008 Ch.19 USART（中断使能）；Cortex-M3 NVIC 编程模型

**applicable_chip**：STM32F103C8T6

**不适用警告**：本条描述两级使能的概念，具体函数名与常量名随库而异；轮询方式接收不需要任何一级中断使能。

## card-24 · NVIC 优先级分组与抢占/响应优先级

**标签**：`nvic` `priority` `preemption` `配置`

**正文**：Cortex-M3 的中断优先级分为抢占优先级与响应（子）优先级，两者占用的位数由优先级分组决定（SPL 中通过 `NVIC_PriorityGroupConfig` 设置）。关键约束是：**整个工程只应设置一次优先级分组**，且填写 `NVIC_InitTypeDef` 中的抢占/响应优先级数值时，必须在当前分组所允许的取值范围内；若分组设为只给抢占优先级 0 位，却填入非零的抢占值，行为将不符合预期。此外，未显式设置优先级时中断使用默认值，多个中断并存时可能出现响应顺序与预期不符，表现为「接收偶发丢字节」而非完全不响应。

**source_ref**：Cortex-M3 通用指南（NVIC 优先级分组）；RM0008 中断相关章节

**applicable_chip**：STM32F103C8T6

**不适用警告**：优先级分组的具体位数与库常量随内核与库版本而异；本条不涉及特定分组取值的推荐。

## card-25 · 中断服务函数名必须与启动文件一致

**标签**：`isr` `startup` `vector` `高频故障`

**正文**：中断服务函数的**函数名本身就是向量表的绑定方式**：启动文件（如 `startup_stm32f10x_md.s`）中为每个中断定义了固定的向量名，工程中定义的 C 函数必须与之完全一致（例如 `USART1_IRQHandler`），链接时才能正确挂接。拼写错误（少一个字母、大小写不符、写成 `USART1_IRQHandle`）不会导致编译报错，只会让该中断向量落到默认的空处理函数上，表现为「中断配置了但永远不进」。此外启动文件需与芯片的 Flash 密度等级匹配（如 md/hd），选错型号会导致外设中断向量定义本身就不对。

**source_ref**：启动文件（startup_stm32f10x_*.s）向量表定义；工具链相关

**applicable_chip**：STM32F103C8T6

**不适用警告**：启动文件的密度后缀（ld/md/hd 等）须与实际芯片 Flash 容量对应；HAL 工程同样依赖向量名一致性。

## card-26 · RXNE 标志的清除方式

**标签**：`usart` `isr` `rxne` `flag` `标志清除`

**正文**：RXNE（接收数据寄存器非空）标志在软件读取接收数据寄存器（`USART_ReceiveData`，本质是对 DR 的读操作）时被清除。这意味着中断服务函数**必须真正执行读取动作**，仅仅进入中断而不读 DR，RXNE 会保持置位，中断被反复触发，表现为程序卡在中断里、主循环完全没有执行机会。反过来，如果在中断外已经读过数据、或在中断里读了但没保存，也会出现「进了中断却拿不到数据」的困惑。因此标准做法是：在 ISR 中先确认标志，再调用接收函数读取字节并存入缓冲区。

**source_ref**：RM0008 Ch.19 USART（状态寄存器与标志清除）

**applicable_chip**：STM32F103C8T6

**不适用警告**：不同标志的清除方式不同，不能套用：RXNE 靠读 DR 清除，TC 需「读 SR 再写 DR」的序列，ORE 需「读 SR 再读 DR」的序列。

## card-27 · TC 与 TXE 的区别及清除序列

**标签**：`usart` `tc` `txe` `flag` `发送`

**正文**：发送相关有两个容易混淆的标志：TXE 表示发送数据寄存器已空（可以写入下一个字节，但字节可能还在移位寄存器中发送），TC 表示发送完成（包括移位寄存器也已发完）。判断「一帧是否发完」应看 TC，判断「能否写入下一字节」应看 TXE。TC 标志的清除需要特定序列：先读状态寄存器、再写数据寄存器（SPL 中通常对应先调用获取标志的函数、再调用发送函数），只查询不清除会让 TC 持续置位，导致依赖 TC 的等待逻辑误判。使用 `printf` 重定向时尤其要注意等待的是哪个标志：等待 TXE 足以保证逐字节写入安全，但程序末尾若要确保最后一字节发出，需等 TC。

**source_ref**：RM0008 Ch.19 USART（状态寄存器与标志）

**applicable_chip**：STM32F103C8T6

**不适用警告**：本条只描述标志语义差异与清除要求，不推荐具体实现方式；中断方式发送时还需配合发送中断使能。

## card-28 · 接收溢出错误 ORE 的处理

**标签**：`usart` `ore` `overflow` `错误` `isr`

**正文**：当上一个字节未被读取、新字节又接收完成时会产生 ORE（过载错误）。若中断服务函数中只处理 RXNE 而不处理 ORE，溢出后接收可能停止工作，表现为「刚开始能收，收一会儿就完全没反应了」。ORE 的清除序列与 RXNE 不同，需要「先读状态寄存器、再读数据寄存器」的顺序，因此不能用处理 RXNE 的同一段代码顺带清掉。排查时若遇到「接收一段时间后失效」的现象，应把 ORE 作为重点怀疑对象，并检查主循环中是否存在长延时、以及 ISR 是否被其他高优先级中断长时间阻塞。

**source_ref**：RM0008 Ch.19 USART（过载错误标志）

**applicable_chip**：STM32F103C8T6

**不适用警告**：ORE 的清除顺序与 RXNE、TC 均不相同，必须分开处理；本条不描述具体寄存器位操作，仅说明处理要求。

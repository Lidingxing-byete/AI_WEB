# 补充决策 · Web Serial API 串口采集（P2-D1）

> 决策时间：2026-10-25 | 决策人：Zero | 触发：风险 R17（本机无串口助手工具）
> 证据标签：本文中的技术约束为 `[静态分析]`（基于浏览器 API 公开行为与本机环境探测），未进行任何实际串口通信。

---

## 一、决策内容

**采纳 Web Serial API**，在本项目前端浏览器中直接读取 USB-TTL 串口数据，用于 Phase 2.5 与 Phase 5 的串口实测证据采集，**不依赖任何第三方串口助手工具**。

---

## 二、为什么采纳

| 理由 | 说明 |
|---|---|
| **消除 R17 阻塞** | 本机无 sscom / XCOM / PuTTY / MobaXterm，venv 无 `pyserial`；不解决则 Phase 2.5「验证串口能否收到数据」无法执行 |
| **证据链更硬** | 采集到的原始字节流直接进入证据链，演示路径为「应用自己读到的数据 → 给出的诊断」，优于「人看串口助手再手敲进网页」 |
| **契合项目定位** | 「证据驱动」是本项目的立身之本；能自采证据比只能接受转述更有说服力 |
| **零安装成本** | 本机 Chrome 与 Edge 均已安装，Web Serial API 为浏览器原生能力，无需下载或安装任何组件 |

本机环境依据（`[静态分析]`）：
- Chrome @ `C:\Program Files\Google\Chrome\Application`
- Edge @ `C:\Program Files (x86)\Microsoft\Edge\Application`

## 二之二、实测设备信息（2026-10-25 14:10 探测，`[静态分析]`）

USB-TTL 已连接，探测结果**对 Web Serial API 有利**：

| 项 | 实测值 |
|---|---|
| COM 口号 | **COM3** |
| 设备实例 ID | `USB\VID_0843&PID_5740&REV_0100` |
| 序列号 | `FX2348N` |
| 兼容 ID | `USB\Class_02&SubClass_02&Prot_01` → **USB CDC-ACM** |
| 驱动 | `usbser.sys`（`usbser.inf`，Microsoft 提供，服务名 `usbser`） |
| 枚举器 | USB |
| 状态 | OK |

**为什么这是好消息**：该设备枚举为标准 **USB CDC-ACM** 类，且使用 Windows 内置的 `usbser.sys` 驱动（而非 CH341/CP210x/FTDI 的厂商专有 VCP 驱动）。这类设备在 Chrome 的 Web Serial API 下是最常见、兼容性最好的一类，不需要额外安装 WinUSB 驱动或替换驱动。

**对 Phase 2.5 的意义**：P2-D1 方案的物理前置条件已满足，11/01 验证时不需要再花时间处理驱动问题。

**遗留待确认 → 已确认（2026-10-25 14:14，用户答复）**：
- ✅ **转换器 IO 电平 = 3.3V**。与 STM32F103 的 3.3V IO 电平一致，**可直接交叉连接 TX/RX 并共地，无需任何电平转换**，不存在 5V 损坏引脚的风险
- ⚠️ 芯片型号未在 CH340 / CP210x / FTDI / PL2303 常见列表中匹配到，但不影响使用（CDC-ACM 由 Windows 通用驱动接管）

## 三、对架构的影响（相对 Phase 1 的范围变更）

### 3.1 新增前端模块

| 路径 | 职责 |
|---|---|
| `components/webserial/` | 串口连接面板、波特率/参数选择、开始/停止采集、字节流展示 |

### 3.2 新增证据类型

`Phase1_数据模型草案.md` 中 `evidence.source_type` 枚举新增一项：

| 原枚举 | 新增 |
|---|---|
| `tool` / `knowledge` / `user_test` / `model` | **`web_serial`** |

证据标签：通过 Web Serial 采集到的字节流属于真实硬件数据，标 **`[实测-硬件]`**。

### 3.3 与「AI 不得代填实测结果」红线的关系（关键）

这条红线**不因本决策而松动**。明确边界：

| 允许 | 禁止 |
|---|---|
| 浏览器采集串口原始字节，作为证据引用 | AI 生成**任何未被采集到的字节** |
| 展示采集到的十六进制/文本视图 | 把采集数据包装成「验证通过」的确定性结论 |
| 用采集字节与预期值做**自动比对**，结果标 `[推断]` | 用推断结果冒充 `[实测-硬件]` |
| 由用户确认「该验证步骤是否通过」 | 系统自动把任务状态迁移为已完成 |

**判定权仍在用户**：采集到的字节是证据，是否构成「验证通过」由用户确认；系统的自动比对结果一律标 `[推断]` 并显式提示需人工确认。

### 3.4 与后端的关系

Web Serial 是**纯浏览器侧能力**，数据不经过后端模型层：

- 采集到的字节流**仅存于浏览器内存与本地存储**，不上传任何服务器
- 仅当用户主动「引用为证据」时，才随任务提交写入本地数据库
- 后端不新增任何串口相关接口（保持 Phase 1 的 17 端点不变）

## 四、技术约束（必须遵守）

| 约束 | 说明 | 影响 |
|---|---|---|
| **必须由用户手势触发** | 浏览器安全策略要求 `requestPort()` 只能在用户点击等手势的调用栈中发起 | UI 必须提供「连接串口」按钮，不能自动连接 |
| **仅 HTTPS 或 localhost** | 非安全上下文不可用 | 开发服务器用 localhost 即满足；在线部署须 HTTPS |
| **浏览器兼容性** | Chrome / Edge 支持；**Firefox 不支持** | 需在 UI 检测并提示；答辩演示须用 Chrome 或 Edge |
| **设备授权由用户完成** | 用户在浏览器弹窗中选择具体串口设备 | 系统不得预设或猜测设备 |
| **独占访问** | 串口被浏览器打开期间，其他程序无法同时访问 | 提示用户先关闭其他串口工具 |

## 五、Phase 3 实现要点

1. 检测 `navigator.serial` 是否存在，不存在则显示降级提示（引导用户改用手动填写实测结果）
2. 「连接串口」按钮 → `requestPort()` → 用户选设备
3. `port.open({ baudRate, dataBits, stopBits, parity, flowControl })`，参数由用户选择，默认 115200 / 8 / 1 / none / none
4. 读取循环：以 `ReadableStream` 持续读取，同时提供十六进制与文本两种视图
5. 「停止采集」释放 reader 与 port
6. 「引用为证据」将选中的字节片段写入任务证据，标 `[实测-硬件]` 且 `source_type = web_serial`

## 六、降级方案

若 Web Serial 不可用（Firefox、无 HTTPS、设备被占用、USB-TTL 未插）：

→ 回退到 Phase 1 原设计：**由用户在表单中手填实测结果**，标 `[实测-硬件]`（用户填）。

这条回退路径已存在于 `record_test_result` 工具，本决策不改变它，只是**新增一条更强的采集通道**。

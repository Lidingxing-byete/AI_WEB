## 二、D1 连带影响：RAG 语料策略重设计

### 问题

原复用评估认为 350+ 条目知识库「可作 RAG 语料底座」。D1 明确不能进仓库后，**评审拿到仓库时看不到任何真实语料**，RAG 6% 失去可验证性，且向量检索无内容可检。

### 结论：仓库内采用「双层知识」结构

| 层 | 内容 | 是否入库 | 作用 |
|---|---|---|---|
| **L1 结构化诊断规则库** | 本项目自撰的 UART 诊断规则：症状 → 候选根因 → 证据检查项 → 引用章节 → 验证步骤 | ✅ 入库 | 工具层查询对象；评审可直接审计每条规则的依据 |
| **L2 向量检索语料** | 本项目自建的诊断知识卡片（目标 40 条） | ✅ 入库 | 满足 RAG 架构要求，提供真实检索行为 |
| L3 本地参考资料 | 官方手册 10 份 PDF、本地知识库 350+ 条目 | ❌ 不入库 | **仅开发期参考**，用于启发规则撰写与事实核对 |

### 入库内容的来源合规红线

| 允许 | 禁止 |
|---|---|
| 寄存器名、位定义、配置流程等**技术事实**（公有事实，不受版权保护） | 手册原文段落、图表、公式排版的复制粘贴 |
| 自撰的诊断规则与案例 | 手册章节的长摘要（改写也不行，需重新组织为规则） |
| 引用标注：`依据 RM0008 第 19 章 USART` | 手册 PDF、章节截图 |
| 官方库 API 名与用法 | 本地知识库条目的原文（即使"已审"） |

### 由此产生的新设计要求

1. L1 规则库需设计**可版本化、可单元测试**的数据结构（Phase 1 定 schema）。
2. L2 卡片需与 L1 规则**关联**，避免两套内容互相矛盾。
3. 引用规范在 Phase 1 统一定义，Phase 2 建库时强制校验。
4. **新增合规检查点**：Phase 8 提交前必须做一次「仓库全文版权扫描」（关键词 + 手册原文比对）。

## 三、D5 连带影响：时间线从 29 天压到 24 天

### 事实

- 今天 2026-10-25，省赛截止 2026-11-18，**剩余 24 天**。
- 每日 4 小时 → 总预算 **96 小时**。
- 原 Phase 0–8 串行预估 29 天 ≈ **116 小时**。
- **缺口 20 小时（17%）** → 必须砍范围，不能靠加班硬扛。

### 削减原则（遵循 `PROJECT_PLAN.md` 第十节优先级）

> 时间不足时优先缩减功能范围，**不得删掉核心测试、硬件真实性检查和比赛交付环节**。

**砍掉（不进入本次参赛范围）**：

| 砍掉项 | 省下 | 理由 |
|---|---|---|
| MCP 协议接入 | ~4h | Function Calling 已满足「工具集成 4%」考察点 |
| 浏览器端推理（Transformers.js / WebGPU） | ~5h | 无直接分值，赛事仅「鼓励」 |
| 真实硬件测量的波形自动分析 | ~4h | 多模态降级为「图片 + 文本联合推理」，不做信号处理 |
| 在线演示部署 | ~4h | 可选加分项，且有稳定性风险 |
| PostgreSQL + pgvector 独立部署 | ~3h | 第一版用 SQLite + 轻量向量存储，避免部署负担 |
| 多案例并行（6 案例全实测） | ~6h | 压缩为 **4 个案例完成完整实测**，另 2 个仅静态分析 |

**保留（不可砍）**：

- 核心诊断闭环（Phase 3）
- 确定性工具层 + Agent 工作流（Phase 4）
- 真实硬件验证（Phase 5）
- 评测与安全回归（Phase 6）
- 三件交付材料：仓库 + 视频 + 技术文档（Phase 8）

## 四、D3 落地方案（多模态最小实现）

| 项 | 方案 |
|---|---|
| 定位 | TX 引脚无波形类故障的**证据补充**，不是独立功能 |
| 实现 | 前端上传波形/示波器截图 → 与文本现象一起送多模态模型 → 输出对波形的客观描述 → 汇入证据面板 |
| 边界 | ❌ 不做信号处理 ❌ 不做自动测量 ❌ 不自动判定根因（只做证据描述） |
| 排期 | Phase 7（6h 内完成） |
| 依赖 | 需一个支持视觉的模型 API（云端或本地多模态），Phase 1 选型时定 |
| 风险 | 若时间不足，**优先砍此项**（丢 5% 分，优于拖垮交付） |

## 五、D4 落地方案（Phase 2.5 硬件最小验证）

**目的**：不等 Phase 5 才发现硬件问题。只做两件事，各 10 分钟：

1. 用 ST-Link 给 STM32F103C8T6 烧录一个最小 UART 工程，确认**能下载、能跑**。
2. 接 USB-TTL，确认**串口有输出**、波特率正常。

**通过标准**：`[实测-硬件]` 标签下有真实的烧录与串口截图/日志。
**不通过**：立即上报（板子/线材/驱动问题），并评估是否放弃部分硬件验证目标。

> 依据 `PROJECT_PLAN.md` 第十一节第 8 条：涉及真实硬件的步骤必须等待用户完成，Agent 不得代替。

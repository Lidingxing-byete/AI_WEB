## 四、三个关键设计决策

### 1. 证据标签做成类型系统，而不是注释约定

`Finding` 与 `Candidate` 在**构造时**强制校验标签，非法标签直接抛 `ValueError`。
这样"忘记打标签"在开发期就崩，而不是等到评审或答辩才暴露。这是红线 #2 的代码层保障。

### 2. 检查三态：`violated` / `ok` / `unknown`

`unknown` 是一等公民。本轮 C1 案例产出 **6 项 unknown**，例如：

- R-S1-05 物理接线（TX/RX 是否交叉）—— 静态不可见
- R-S2-01 HSE_VALUE 与实际晶振是否一致 —— 需用户提供晶振频率
- R-S6-03 中断标志是否清除 —— 需读 ISR 函数体，本版未做

**这些绝不包装成确定结论**，而是转成「需要什么才能判定」的提示给用户。

### 3. 被注释掉的初始化调用单独检出

`cparse.split_comments()` 在剥离注释时保留原文，并能检出
「RCC_APB2PeriphClockCmd 只存在于注释里」这类情况——这正是案例 C1 的实际注入手法。
只做"是否存在调用"的判断会漏掉这一类。

## 五、已知局限（如实声明，不掩饰）

| 局限 | 影响 | 计划 |
|---|---|---|
| 结构体赋值追踪只处理「变量.字段 = 值」，不追踪指针别名 | 少数写法会漏检 | Phase 4 视需要加强 |
| 条件编译与函数式宏未做展开 | 分支内配置可能漏检 | 已在输出 `limitations` 中提示用户 |
| **波特率只做正向计算**：给定实际总线时钟算应写 BRR，尚未做「代码实际写入值 vs 应写值」的反向比对 | HSE_VALUE 不符（C2）这类故障目前只能靠 R-S2-01 的 unknown 提示，无法量化 | **Phase 4 补** |
| 未做中断服务函数体级分析 | R-S6-03 / R-S6-04 只能返回 unknown | Phase 4 补 |
| 无 SQLite 持久化，报告只在内存 | 任务无法回溯 | 第二批随 API 一起做 |

# Phase 1 交付物 ⑥ 技术选型比较

> 证据标签：本机环境类结论为 `[静态分析]`（2026-10-25 实测核查，见附录 A）；其余为 `[推断]`（工程判断）。
> 本文不含性能基准数字、不含准确率承诺。
> 生成时间：2026-10-25。所属阶段：Phase 1。

## 零、选型总表（结论前置）

| 层 | 选型 | 关键理由 |
|---|---|---|
| 前端框架 | **React 18 + TypeScript** | 赛事重点考察前端；生态与类型安全 |
| 构建 | **Vite** | 启动快、配置少、无 SSR 需求 |
| UI 样式 | **Tailwind CSS** | 开发速度快，无需设计系统即可达到整洁观感 |
| 状态管理 | **Zustand** | 轻量，避免 Redux 样板代码 |
| 后端 | **Python 3.13 + FastAPI** | 文本解析生态强；自带 OpenAPI；Pydantic 校验天然适配工具参数 |
| 云端模型 | **可配置 provider（DeepSeek 优先）** | 赛事要求 provider 可配置；不得锁定单一厂商 |
| 本地模型 | **Ollama + qwen2.5:7b / qwen2.5-coder:7b** | **本机已拉取，零下载成本** |
| 嵌入模型 | **bge-m3（Ollama）** | **本机已拉取**，中文语义优于 nomic-embed-text |
| 检索 | **BM25 + bge-m3 向量 混合** | 语料小但需语义召回；两者本地均可用 |
| 存储 | **SQLite + 本地文件** | 零部署，评审可一键复现 |
| Agent 编排 | **自研轻量状态机** | 可解释、可复现，满足赛事「须能解释全部代码」 |
| C 代码解析 | **正则 + 轻量语法解析（不编译）** | 安全红线：绝不执行用户代码 |

## 一、前端框架

| 候选 | 优势 | 劣势 | 结论 |
|---|---|---|---|
| **React 18 + TS** | 生态最大、评委熟悉度高、类型安全利于工程质量评分 | 需自行组织状态 | ✅ **选中** |
| Vue 3 + TS | 上手快、SFC 直观 | 复杂诊断界面生态组件略少 | 备选 |
| Next.js | SSR、路由完备 | 本项目无 SSR/SEO 需求，反而增加构建复杂度与解释成本 | ❌ 不选 |
| 原生 HTML/JS | 零依赖 | 三栏工作台 + 流式时间线维护成本高，不利于「前端工程质量」评分 | ❌ 不选 |

**依据**：`PROJECT_PLAN.md` 第六节明确「界面应围绕诊断任务组织」，三栏工作台 + 流式更新组件化收益明显；赛事「前端工程质量 10%」需体现工程化水平。`[推断]`

## 三、UI 样式方案

| 候选 | 优势 | 劣势 | 结论 |
|---|---|---|---|
| **Tailwind CSS** | 无需自建设计系统即可保证整洁一致；类名即样式，修改快 | HTML 类名较长 | ✅ **选中** |
| Ant Design | 组件齐全（表格、表单、步骤条现成） | 默认视觉"后台管理系统"感强，定制成本高 | 备选（若表单/表格工作量超预期，可局部引入） |
| CSS Modules | 无额外依赖 | 需自己写大量样式，时间预算不允许 | ❌ |

**补充决策**：诊断时间线与证据面板是定制 UI，组件库帮助有限；但 P2 表单、P4 验证清单可用现成表单能力。倾向 Tailwind 为主，不引入重型组件库。

### 5.1 Python 解释器版本（**本机实测结论**）

| 项 | 实测结果（`[静态分析]` 2026-10-25） |
|---|---|
| PATH 首个 `python` | `3.14.3`（托管版） |
| 托管版 3.13.12 | 实际为 `3.13.14` |
| 默认 venv | `C:\Users\Zero\.workbuddy\binaries\python\envs\default\Scripts\python.exe` → **3.13.14，已存在** |

**决策**：使用**默认 venv（Python 3.13.14）**，不用 3.14.3。

理由（`[推断]`）：3.14 属新近大版本，部分带 C 扩展的 AI/数据处理包可能尚未提供 Windows wheel，存在安装失败风险；3.13 兼容性成熟，且托管 venv 已就绪、符合依赖隔离要求。

**风险提示**：3.14.3 是当前 PATH 首选，实施时若误用会带来依赖安装失败。Phase 3 启动时需显式指定解释器路径并写入项目说明。

## 八、RAG 检索方案

| 候选 | 优势 | 劣势 | 结论 |
|---|---|---|---|
| **BM25 + bge-m3 向量（混合）** | 关键词命中准 + 语义召回全；全本地、零下载；BM25 部分可解释 | 需实现融合排序 | ✅ **选中** |

**融合策略**（`[推断]`，Phase 3 落地时可调）：规则库命中优先（确定性）→ BM25 与向量各自 Top-K → 加权合并 → 每条结果附 `source_ref`。

**语料合规**（D1 决策）：L1 规则库与 L2 知识卡片**全部自撰**；官方手册与本地 350+ 条知识库**不入库**，仅开发期参考。详见 `Phase1_系统架构说明.md` 第五节。

## 十、Agent 编排

| 候选 | 优势 | 劣势 | 结论 |
|---|---|---|---|
| **自研轻量状态机 + 工具注册表** | 流程确定、可复现；代码量小，**能解释全部逻辑**（赛事硬性要求）；trace 完全自控 | 需自己写工具调用解析与重试 | ✅ **选中** |
| LangChain | 开箱即用、组件多 | 抽象层多，输出行为不易精确控制；答辩解释成本高 | ❌ |
| LangGraph | 状态机语义契合、可持久化 | 学习成本 + 内部行为需额外解释；版本迭代快 | ❌ |
| 纯 Prompt 让模型自由规划 | 实现最简 | 不可复现、易跑偏，违背创新方向 B | ❌ |

## 十一、C 代码解析方式

| 候选 | 优势 | 劣势 | 结论 |
|---|---|---|---|
| **正则 + 轻量结构化解析（静态）** | 零外部依赖；**绝不执行用户代码**（安全红线 SEC-01） | 对复杂宏/条件编译覆盖有限 | ✅ **选中** |
| 调用 Keil / GCC 编译 | 信息最全 | ❌ 违反安全红线（执行用户代码）；引入环境依赖，评审无法复现 | ❌ 明确排除 |
| Clang AST（libclang） | 解析精准 | 需装 LLVM 依赖；体积大 | ❌ 时间预算不允许 |
| tree-sitter | 解析较好、有 C 语法 | 需装依赖、需学习绑定 | 备选（若正则覆盖不足再评估） |

**容错设计**：解析不出的部分**如实标注**「未解析」，不猜测、不静默（对应异常流程 E-03）。

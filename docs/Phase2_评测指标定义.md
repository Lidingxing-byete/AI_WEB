# Phase 2 交付物 ④ 评测指标定义

> 证据标签：指标设计为 `[推断]`。**当前无任何评测数据**，全部指标为待测量项。
> 生成时间：2026-10-25。所属阶段：Phase 2。
> 对应 `PROJECT_PLAN.md` Phase 2 输出「评测指标定义」与 Phase 6 任务要求。

---

## 一、评测目标

回答三个问题，而不是追求一个漂亮数字：

1. **能不能定位**：系统能否在候选根因中包含真正的故障原因？
2. **凭什么这么说**：给出的证据是否真实、可追溯、无幻觉？
3. **知道不知道**：证据不足时，系统是否诚实显示「不确定」？

---

## 二、指标体系

### 指标 1 · 根因命中

| 指标 | 定义 | 判定 |
|---|---|---|
| **Top-1 命中率** | 正确根因排在首位的用例占比 | 以 `Phase2_UART故障案例规范.md` 的标准答案为准 |
| **Top-3 命中率** | 正确根因出现在前 3 个候选中的用例占比 | 同上 |
| **漏检率** | 正确根因**完全未出现**在候选列表中的用例占比 | 越接近 0 越好 |

### 指标 2 · 证据质量

| 指标 | 定义 |
|---|---|
| **证据正确率** | 系统给出的证据中，经人工核对为真实成立的占比 |
| **幻觉证据率** | 引用了**材料中不存在**的代码行、配置项或日志内容的证据占比（应趋近 0） |
| **证据可追溯率** | 能点开查看来源（工具调用 ID 或知识卡片 + `source_ref`）的证据占比（目标 100%） |
| **反对证据呈现率** | 是否显式列出反对证据，或明确声明「未见反对证据」（防止只报喜） |

> **幻觉证据率是本项目的关键指标**。编造证据比答错更严重——它直接摧毁「证据驱动」这一核心定位。

### 指标 3 · 验证步骤质量

| 指标 | 定义 |
|---|---|
| **可执行率** | 用户能按描述实际操作的步骤占比（含明确的操作、测量点、预期结果、所需工具） |
| **判别力** | 执行后能否得出明确结论（能区分「符合预期 / 不符合预期」）的步骤占比 |
| **安全性** | 涉及接线/供电的步骤是否附带安全提示 |

### 指标 4 · 不确定性校准

| 指标 | 定义 | 判定场景 |
|---|---|---|
| **应不确定时是否不确定** | 负例 N-01（材料不足）是否未给出高置信度唯一根因 | 给出唯一根因 → 记为**校准失败** |
| **误判率** | 给出唯一根因但根因错误的用例占比 | 负例中任一命中即为严重问题 |
| **降级诚实度** | 模型不可用时是否明确告知降级，且输出标签正确（仅 `[静态分析]`） | 未告知 → 记为失败 |

### 指标 5 · 工程与稳定性

| 指标 | 定义 |
|---|---|
| **工具调用成功率** | 工具调用中返回 `ok` 的占比；失败是否被如实记录（不得静默） |
| **trace 完整率** | 每次诊断是否留下完整的步骤与工具调用记录（对应「可追溯」） |
| **输出稳定性** | 同一用例多次运行，Top-1 根因一致的比例 |
| **降级可用性** | 断网 + 无本地模型时，系统是否仍能给出确定性检查结果 |

## 三、与纯 LLM 基线的公平比较设计

`PROJECT_PLAN.md` Phase 6 要求「与纯 LLM 基线进行公平比较」。公平性通过以下约束保证：

| 约束 | 做法 |
|---|---|
| 同一模型 | 基线组与实验组使用**同一模型与同一关键参数**（temperature 等） |
| 同一材料 | 输入完全一致 |
| 同一输出要求 | 基线组也要求输出「候选根因 + 证据 + 验证步骤」，便于同维度比较 |
| 唯一差异 | 实验组额外具备：诊断工具调用 + 自建知识库检索 + 编排流程 |
| 多次运行 | 每用例 ≥3 次，比较**分布**而非单次结果 |
| 评判前置 | 判定标准在跑测试前由本文档固定，**不得事后调整** |

**基线组提示词原则**：不人为弱化基线（不故意写糟糕的提示），否则比较无意义。

## 四、评分与判定规则

| 规则 | 说明 |
|---|---|
| 判定基准 | 以 `Phase2_UART故障案例规范.md` 中各案例的「正确根因」为唯一标准答案 |
| 干扰项处理 | 干扰项出现在候选中**不扣分**（合理的多候选是设计目标）；但干扰项排 Top-1 则记为误判 |
| 证据核对人 | 由用户（具备 STM32 知识）人工核对证据真实性 |
| 争议处理 | 判定有争议时**保守处理**，记为「不确定」而非计入成功 |
| 反自证偏差 | 禁止用「模型自己说它对」作为正确性依据（`PROJECT_PLAN.md` 第四节明确禁止） |

## 五、结果呈现规范（硬性）

✅ **必须呈现**：
- 样本数量与测试条件（模型名、参数、运行次数、是否降级）
- 各指标的**原始计数**（如「6 个正例中 Top-1 命中 X 个」），而非只给百分比
- 局限性说明（见第六节，必须原样包含）
- 失败用例的具体分析

❌ **严禁**：
- 用 6～9 个样本宣称「准确率 XX%」并对外宣传
- 只报成功用例、隐去失败用例
- 把 `[静态分析]` 或未实测的结果写成 `[实测-硬件]`
- 与基线对比时夸大差距（样本小，差距不具统计显著性）
- 用「显著优于 / 提升 XX%」等未经统计检验的表述

**推荐表述示例**（供 Phase 6 使用）：

> 在 6 个自撰的 STM32F103C8T6 USART 故障用例上，本系统的 Top-1 命中 X/6，纯 LLM 基线为 Y/6。
> 样本量小且场景单一，该结果**仅用于说明方法差异，不构成准确率声明**。

## 六、局限性声明（Phase 6 报告必须原样包含）

| # | 局限 |
|---|---|
| 1 | 用例仅 9 个（6 正 + 3 负），**不具备统计显著性** |
| 2 | 场景限定为 STM32F103C8T6 + USART1 + 标准外设库，不推广到其他芯片或外设 |
| 3 | 用例材料由本项目自撰，与真实工程复杂度存在差异 |
| 4 | 每用例运行次数有限，不足以刻画输出波动全貌 |
| 5 | 6 个案例中仅 4 个有硬件实测计划，C4、C6 仅为静态分析 `[待验证]` |
| 6 | 证据真实性由人工核对，存在主观判断成分 |
| 7 | 未覆盖真实用户输入的噪声（不完整代码、口语化描述、错误分类） |

## 七、回归测试

| 触发时机 | 范围 |
|---|---|
| Phase 6 建立基线 | 全量 9 个用例 × 3 次 |
| 此后每次重大改动（工具、提示词、编排逻辑、模型切换） | 全量重跑，与基线对比 |
| Phase 8 提交前 | 全量重跑一次，确认无回退 |

**回归失败处理**：若某指标较基线明显变差，**先记录并分析原因**，不得修改评测标准来"通过"。

# 芯诊 AI · 云服务器部署说明（子路径 + 云端 AI 为主）

> 目标形态：`https://你的域名/xz/` 打开演示页，`/xz/api/` 反代到本机 8787。
> 与博客**共存**：博客根路径不动，只多两个 location。
> 模型：**云端 DeepSeek 为主**；服务器上没有 Ollama 也不影响（自动降级到规则层）。
> 证据纪律：部署不改变任何诊断结论口径，系统内仍无 `[实测-硬件]`。

---

## 0. 前置条件

| 项 | 要求 | 检查 |
|---|---|---|
| Python | **≥ 3.10**（代码用了 `str \| None`） | `python3 -V` |
| 磁盘 | ≥ 300MB（依赖 + 数据） | `df -h /` |
| 端口 | 8787 仅监听 127.0.0.1 | `ss -lntp \| grep 8787` |
| Nginx | 已在跑，HTTPS 证书可用 | `nginx -v` |
| 备案 | 用**已有域名 + 子路径**，不需要新增备案 | — |

> 若 `python3` 是 3.8/3.9：不要动系统 python3。Ubuntu 用
> `apt install python3.11 python3.11-venv`（或 deadsnakes PPA）；
> 宝塔面板用「Python 项目管理器」建 3.11 环境。

## 1. 手动分步版：准备目录与虚拟环境

> 阿里云用户可直接跳到 §10 用一条命令装完；本节留给脚本不适用/想自己控制每一步的场景。

```bash
sudo useradd -r -s /usr/sbin/nologin xinzhen 2>/dev/null || true
sudo mkdir -p /opt/xinzhen/{apps,web}
sudo chown -R "$USER": /opt/xinzhen

# 上传代码（在本地执行）：只传后端与语料，不传 node_modules / data
#   rsync -av --exclude data --exclude __pycache__ \
#     apps/server/ root@你的域名:/opt/xinzhen/apps/server/
#   rsync -av docs/corpus/ root@你的域名:/opt/xinzhen/docs/corpus/

cd /opt/xinzhen
python3 -m venv venv
./venv/bin/pip install --upgrade pip
./venv/bin/pip install -r apps/server/requirements.txt   # 只有 fastapi / uvicorn / pydantic
```

**语料路径要求**：`app/config.py` 里 `CORPUS_DIR = 仓库根/docs/corpus`，
按上面的目录布局，仓库根就是 `/opt/xinzhen`，所以语料要落在
`/opt/xinzhen/docs/corpus/`（含 `l1_rules_uart.json`、`cards/`、`phenomena_map.json`）。

## 2. 配置环境变量（云端为主）

```bash
cp /opt/xinzhen/apps/server/../deploy/env.production.example /opt/xinzhen/apps/server/.env
# 或手动创建 /opt/xinzhen/apps/server/.env，内容参考 deploy/env.production.example
chmod 600 /opt/xinzhen/apps/server/.env
sudo chown xinzhen: /opt/xinzhen/apps/server/.env
```

要点：
- `XZ_LLM_PREFERRED=cloud` —— 云端优先；
- `XZ_CLOUD_API_KEY` **留空**：云端调用由**测试者填自己的 Key**（页面内即填即用，
  只存他的浏览器标签页，服务端不保存），站长不需要预置任何密钥；
- 服务端不再有"密钥管理接口"，因此不需要管理口令；需要的是**限流**（见 §9）。

---

## 3. 启动后端（systemd）

```bash
sudo cp deploy/xinzhen.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now xinzhen
systemctl status xinzhen --no-pager
curl -s http://127.0.0.1:8787/api/health | head -c 300
```

`health` 里应能看到 `"model_layer":{"provider":"cloud+local+rule", ... "cloud_configured":false}`，
表示三级链已就位、云端待填密钥。

> 为什么必须 `--workers 1`：SSE 走进程内队列、SQLite 单文件、引擎是进程内单例。
> 多 worker 会出现"诊断流连到另一个进程"的假故障。

---

## 4. 构建并上传前端（子路径）

在**本地**仓库执行：

```bash
cd apps/web
VITE_BASE=/xz/ npx vite build      # Windows PowerShell: $env:VITE_BASE='/xz/'; npx vite build
rsync -av dist/ root@你的域名:/opt/xinzhen/web/
```

必须带 `VITE_BASE=/xz/`：否则资源按根路径加载，`https://域名/xz/` 会白屏。
构建后 `dist/index.html` 里的资源应为 `/xz/assets/...`，可本地 `grep '/xz/assets' dist/index.html` 核对。

---

## 5. 接入 Nginx

把 `deploy/nginx-xz-snippet.conf` 里的两段 `location` 放进博客的 HTTPS `server{}`：

```bash
sudo nginx -t && sudo systemctl reload nginx
```

访问 `https://你的域名/xz/`，应看到三栏工作台，顶栏「后端已连接」。
SSE 是否正常，看诊断时中栏步骤是否**逐条出现**（而不是最后一次性刷出）。

## 6. 云端密钥：测试者自带（站长零配置）

上线后你自己打开页面 → 中栏底部「模型解读 → 我的云端密钥 → 填写我的密钥」，
粘贴**评审/测试者自己的** DeepSeek Key →「保存并校验」。

- 校验只做一次 `GET /models` 鉴权探测，**不触发计费推理**；
- 密钥只存**该浏览器标签页**（`sessionStorage`），关闭标签页即消失；
- 只随请求头 `X-Cloud-Key` 发到后端内存，用完即丢：不写数据库、不写文件、不写日志、不进 URL；
- 页面顶部常驻琥珀色提示：「测试结束请点删除密钥」，右侧按钮一键清除；
- 任何响应只回掩码（`sk-ab…cd90`），后端没有"读取密钥"的接口。

### 演示话术建议（给评审）

> 「云端模型是可选的解释增强。你可以用**自己的** API Key 体验，密钥只存在你这个标签页里，
> 关掉页面或点删除就没了，我们服务端不保存任何人的密钥。不想用也可以——系统会自动降级到
> 本地/规则层，诊断能力不受影响。」

### 站长兜底（可选，不推荐在公开演示用）

若你确实想让所有访客共用一把钥匙，才在 `.env` 填 `XZ_CLOUD_API_KEY` 并重启。
**代价**：任何人都能消耗你的额度，且无法针对单个访客撤销；省赛演示阶段不建议这样做。

## 7. 上线后自检（按顺序）

```bash
# 1) 健康检查（含语料条数）
curl -s https://你的域名/xz/api/health
# 2) 模型状态（未带密钥时应显示 configured=false，且不报错）
curl -s https://你的域名/xz/api/llm/status | head -c 400
# 3) 真跑一轮诊断（浏览器点「C1 故障版」，看步骤是否流式出现）
```

再对照 `deliverables/提交前终检清单.md` 的记录一次回归（本机或服务器均可）。

---

## 8. 回滚

```bash
sudo systemctl stop xinzhen            # 停后端，博客不受影响
sudo rm -f /etc/nginx/conf.d/xz.conf   # 若你把片段单独放这里
sudo nginx -t && sudo systemctl reload nginx
```

前端目录 `/opt/xinzhen/web` 整体删除即恢复原状；SQLite 在
`/opt/xinzhen/apps/data/`，删目录前先备份（服务端不存任何人的密钥）。

## 9. 已知限制（如实说明）

1. 服务器无 Ollama 时，本地模型层恒为「离线」，模型解读只能靠云端；
2. 云端按量计费，公开演示建议加 `auth_basic` 与用量观察（`llm_calls` 表有每次调用记录）；
3. 单 worker + SQLite 适合演示规模（几十并发以内），不适合生产高并发；
   `POST /api/llm/verify-key` 已做 6 次/分钟/单 IP 的限流，其余接口建议在 Nginx 层再加限流；
4. 数据保留在服务器本地，未做备份与清理任务——演示结束可整体删除 `data/`；
5. 本项目仍**没有任何 `[实测-硬件]` 结论**，部署不改变这一点。

## 10. 阿里云专用：zerovoidlog.cn + 现有 Next.js 博客（一条命令）

> 适用环境（来自你提供的 `zerovoidlog.cn.conf`）：**Alibaba Cloud Linux 3**、
> Nginx 用 `/etc/nginx/conf.d/*.conf`、博客是 Next.js 反代 `127.0.0.1:3000`、
> 域名 `zerovoidlog.cn` / `www.zerovoidlog.cn`。
> 芯诊 AI 只占 `/xz/` 前缀，**不碰博客的任何现有配置**（安装脚本只做"插入一个 location 块"）。

### 10.1 前置检查（在服务器终端执行，只读）

```bash
nginx -v; python3 -V; grep -n "listen" /etc/nginx/conf.d/zerovoidlog.cn.conf
```
- `grep listen` 里若**没有 443**：先上证书（见 10.4），否则云端密钥会走明文 HTTP；
- Python 若不是 3.9+：安装脚本会自动 `dnf install python3.9`。

### 10.2 一条命令装后端（含 Nginx 插入）

**方式 A（推荐，服务器能连 GitHub）**

```bash
curl -fsSL https://raw.githubusercontent.com/Lidingxing-byete/AI_WEB/main/deploy/install_on_aliyun.sh -o /tmp/xz-install.sh
sudo bash /tmp/xz-install.sh
```

**方式 B（服务器拉不动 GitHub 时）：传两个文件上去再跑**

在本机准备两个文件（都在 `deploy/` 下）：
- `install_on_aliyun.sh`（安装脚本）
- `xinzhen-src.tar.gz`（代码离线包，约 200KB）

用阿里云客户端的 SFTP 面板传到 `/tmp/`，然后：

```bash
sudo bash /tmp/install_on_aliyun.sh
```
脚本发现 `/tmp/xinzhen-src.tar.gz` 会直接解压，不再访问 GitHub。

脚本做的事（幂等，可重复跑）：
1. 找/装 Python 3.9+；
2. `git clone` 公开仓库到 `/opt/xinzhen`（后续 `git pull` 更新）；
3. 建 `venv` 装 3 个白名单依赖；
4. 生成 `apps/server/.env`（`chmod 600`，云端优先 `XZ_LLM_PREFERRED=cloud`）；
5. 建运行用户 `xinzhen`、装 systemd（单 worker，SSE 必须）并启动；
6. `curl /api/health` 自检；
7. 把 `deploy/nginx-xz-snippet.conf` 插入 `zerovoidlog.cn.conf`（**先备份**；若已有 443 块则插进 443，否则插 80；`nginx -t` 失败自动回滚、不 reload）。

### 10.3 上传前端（在你本机执行，dist 已按 `/xz/` 构建）

```bash
# 方式 A：scp（把 <服务器IP> 换成你的）
scp -r "C:/Users/Zero/Desktop/比赛/apps/web/dist/"* root@<服务器IP>:/opt/xinzhen/www/xz/

# 方式 B：用阿里云客户端的 SFTP 面板，把 dist 目录内全部文件传到 /opt/xinzhen/www/xz/
```

传完在服务器执行：

```bash
chown -R xinzhen:xinzhen /opt/xinzhen/www
systemctl reload nginx
curl -s https://zerovoidlog.cn/xz/api/health
```

### 10.4 证书（若 10.1 没看到 443）

```bash
sudo dnf install -y certbot python3-certbot-nginx
sudo certbot --nginx -d zerovoidlog.cn -d www.zerovoidlog.cn
```
certbot 会把你 `conf.d/zerovoidlog.cn.conf` 改成 443 + 80 跳转；**改完重跑一次安装脚本**，
它会把 `/xz/` 块插进新的 443 server 块（已存在则跳过）。

### 10.5 上线自检

```bash
curl -s https://zerovoidlog.cn/xz/api/health
curl -s https://zerovoidlog.cn/xz/api/llm/status | head -c 300
```
浏览器打开 `https://zerovoidlog.cn/xz/`：顶栏「后端已连接」→ 点「C1 故障版」→
中栏步骤应**逐条流式**出现（一次性刷出说明 SSE 被缓冲，检查 `proxy_buffering off` 是否生效）。

### 10.6 回滚

```bash
ls -lt /etc/nginx/conf.d/zerovoidlog.cn.conf.bak.* | head -1   # 找到最近备份
sudo cp /etc/nginx/conf.d/zerovoidlog.cn.conf.bak.<时间戳> /etc/nginx/conf.d/zerovoidlog.cn.conf
sudo nginx -t && sudo systemctl reload nginx
sudo systemctl disable --now xinzhen
```

### 10.8 限流（已在线启用）

`ash
# 1) 放限流区定义（http 上下文）
sudo cp deploy/nginx-xz-limit.conf /etc/nginx/conf.d/xz-limit.conf
# 2) 在 /xz/api/ 里加两行（snippet 已包含）
#    limit_req  zone=xz_api burst=60 nodelay;
#    limit_conn xz_conn 20;
sudo nginx -t && sudo systemctl reload nginx
`
实测：连续 120 次请求 → 78×200 + 42×429；正常演示（每轮约 10 个请求）不受影响。
如需改成口令访问，在 /xz/ 与 /xz/api/ 各加 uth_basic 两行即可（见 10.5 注释）。

### 10.7 与博客共存的注意事项

- 博客的 `location /` 里有 `proxy_set_header Connection "upgrade"`（Next.js 需要），
  `/xz/api/` 里必须显式改回 `""`，否则 SSE 会被当成 WebSocket 升级而中断——snippet 已处理；
- 博客 `client_max_body_size 20M` 在 server 级生效，`/xz/api/` 单独限到 5m，避免被塞大文件；
- 不要把 `/xz/` 写成 `location /xz`（少了斜杠会误匹配 `/xzfoo`）；
- 更新代码：`cd /opt/xinzhen && git pull && systemctl restart xinzhen`（前端需重新构建上传）。

## 11. 运维：备份与数据清理（已在线上启用）

公开演示允许任何人建任务，SQLite 会持续增长；同时演示数据不属于交付物，丢了也无所谓，
但**不该让磁盘和列表无限膨胀**。所以装了两个小脚本：

| 脚本 | 作用 | 定时 |
|---|---|---|
| `deploy/ops/backup_db.sh` | 用 SQLite 在线 backup API 备份（服务运行中也安全），gzip 保留最近 14 份 | 每天 03:30 |
| `deploy/ops/prune_tasks.py` | 彻底删除 N 天前的任务及其子表（含 `evidences`、`test_results` 的间接关联） | 每周日 04:10（默认 7 天） |

安装（root）：

```bash
install -m 755 deploy/ops/backup_db.sh   /opt/xinzhen/ops-backup.sh
install -m 644 deploy/ops/prune_tasks.py /opt/xinzhen/ops-prune.py
crontab -e     # 参考 deploy/ops/crontab.example 追加两行（不要覆盖已有条目）
```

手动执行：

```bash
bash /opt/xinzhen/ops-backup.sh                    # 立刻备份
/opt/xinzhen/venv/bin/python /opt/xinzhen/ops-prune.py --dry-run   # 只看会删多少
/opt/xinzhen/venv/bin/python /opt/xinzhen/ops-prune.py --days 0    # 清空演示数据
```

日志：`/var/log/xinzhen-ops.log`；备份目录：`/opt/xinzhen/backups/`。

> 已知坑（已修）：`test_results` 是通过 `verification_id` 关联的，不是 `task_id`；
> 第一版清理脚本直接按 `task_id` 删会报 `no such column: task_id`，
> 事务回滚保住了数据，现已按"先删 evidences/test_results，再删带 task_id 的表"修正。
